1. Two AI paths

Every AI call in the backend goes through one boundary: apps/backend/src/ai/gemini.client.ts. From there the app branches into two independent mechanisms:

Path B — one-shot JSON

A single prompt in, a single Zod-validated JSON object out. No conversation, no tools.

prompt.ts→ generateJson()→ schema.safeParse()

Path C — agent loop

Multi-turn: the model can call backend tools and see their results before answering.

AgentLoop.run()→ generateWithTools()→ tool.run()→ loop

Model fallback chain (when GEMINI_MODEL is unset): gemini-3.5-flash-lite → gemini-flash-lite-latest → gemini-2.5-flash. If GEMINI_MODEL is set in .env, it overrides the chain entirely — only that one model is tried.

2. Path B — one-shot features

"Fails open" = if the AI call itself errors, the checker silently assumes the charitable answer rather than blocking the user. Only persona-classifier is fail-loud.

3. Path C — agent loop

Lives in apps/backend/src/ai/agent/:

  • agent-tool.ts — AgentTool wrapper: model-facing JSON-schema description + a separate Zod argsSchema validated at execution time. Throws ToolRejectedError or InvalidToolArgumentsError for the two "expected" failure modes.
  • agent-loop.ts — AgentLoop.run() drives up to DEFAULT_MAX_STEPS = 5 rounds. Each round: call the model → if it requested tool calls, run them and feed results back → repeat. If the step limit is hit, forces one final text-only call.
for (let step = 0; step < maxSteps; step++) {
  const turn = await gemini.generateWithTools({ systemInstruction, contents, functionDeclarations });
  if (!turn.toolCalls.length) return { text: turn.text, ... };   // done
  contents.push(modelTurn(turn.text, turn.toolCalls));            // record the request
  const responses = await Promise.all(turn.toolCalls.map(invoke));
  contents.push({ role: 'user', parts: responses });              // feed results back
}

This round-trip — request a tool call, then replay the conversation with the result — is exactly where the real API call currently breaks. See §7.

4. CoachBot spec

CoachBot is a seeded user inside the existing chat system (Chat / Message / ChatGateway) — no dedicated screen, it's just a DM thread. Two independent ways it talks to the user:

Proactive (cron-driven, deterministic + phrased)

coach.rules.ts→ band (EXCELLENT/GOOD/SLIPPING/AT_RISK)→ coach-phrasing (Gemini, Path B)→ chat message

The rule engine computes the 7-day completion rate + streak and picks the verdict and tip before the model ever runs — Gemini only rewrites the copy into the user's persona voice. If phrasing fails, the raw templated line from coach.templates.ts is sent verbatim. Verified working against the real API in this pass (see §6).

Cron: daily 0 20 * * *, weekly 0 18 * * 0 (Sunday) — deliberately offset from the Monday 09:00 persona-drift scheduler. Idempotent per day.

Reactive (agent loop, POST /coach/chat)

Six tools in coach.toolset.ts, each scoped to userId closed over server-side (the model can never supply its own userId — structural IDOR protection):

  • get_progress_summary, get_habit_list, get_persona_profile, get_active_goal
  • check_persona_drift — expensive; cached per session (internally re-uses the Path B persona-drift-detector)
  • propose_change — stages exactly one change per conversation, re-validated server-side

coach.policy.ts gates every proposal deterministically:

ProposalRule
Persona switchRequires a prior check_persona_drift call in-session that detected drift matching the new persona.
Adjust difficulty ↑Requires ≥ 80% completion rate.
Adjust difficulty ↓Requires < 50% completion rate.
Forfeit goalAll linked habits at streak 0 with avg consistency < 30%.

Rejections come back as { rejected: reason } (distinct from { error } for real tool failures) so the model can explain honestly instead of the proposal silently vanishing.

Fallback ladder (applies to both paths)

  1. One Gemini model fails → try the next in the chain (only if GEMINI_MODEL is unset).
  2. All models fail / empty reply → deterministic weekly summary computed from coach.rules.ts directly from the DB. Any staged proposal is dropped here, since its explanation never reached the user.
  3. DB itself unreachable → static COACH_OFFLINE_REPLY.

API surface

5. Security guardrails

  • PROMPT_SAFETY_GUARDRAIL injected into every prompt — prompt-injection defense + no inference on protected attributes.
  • All Path B outputs Zod-validated before use; malformed JSON → hard error, never passed through.
  • MAX_REPLY_LENGTH = 1000 enforced on coach replies.
  • userId is never supplied by the model — the toolset is opened per-session as toolset.open(userId), closing over the authenticated user. A tool cannot act on someone else's data even if the model hallucinates an id.

7. Findings and fixes applied

Both blocking findings below were fixed and re-verified against the real Gemini API and the real Android app in this same pass — not just diagnosed.

Finding 1 — Backend — FIXED

The reactive agent loop couldn't complete a real tool call

Every POST /coach/chat message that needed a tool fell back to the canned weekly-summary reply, with toolsUsed: []. Server logs showed:

there are non-text parts functionCall,functionCall,functionCall in the response...
ERROR: all Gemini models exhausted
  err: "got status: 400 Bad Request. Function call is missing a thought_signature
        in functionCall parts. This is required for tools to work correctly..."

Root cause: Gemini's "thinking" models (gemini-3.5-flash-lite) attach a thoughtSignature to each function-call part and require it echoed back on the next turn. agent-loop.ts reconstructed the model's turn from just {name, args}, dropping the signature. The installed SDK (@google/genai@0.14.1) made this structurally impossible to fix in application code alone — its response deserializer (partFromMldev) used a hand-written field whitelist that didn't even include thoughtSignature, so it never survived parsing regardless of what the client code read.

Fix applied:

  • Upgraded @google/genai from 0.14.1 → 2.17.1 (current npm latest) — confirmed the new SDK's Part type and deserializers both carry thoughtSignature through.
  • gemini.client.ts::generateWithTools() now reads response.candidates[0].content.parts directly (instead of the lossy response.functionCalls convenience getter) so thoughtSignature is captured alongside each functionCall.
  • ToolCallRequest gained an optional thoughtSignature field; agent-loop.ts::modelTurn() now re-attaches it when replaying the model's turn back to Gemini.

Verified: turbo run build clean, all 437 tests still pass, and live against the real API: get_progress_summary tool calls succeed, a policy-rejected propose_change (difficulty increase at 14% completion) returns a real explanation instead of vanishing, and a valid proposal (difficulty decrease) stages, confirms via POST /coach/chat/confirm, and actually regenerates easier daily habit variations.

Finding 2 — Mobile integration — FIXED

The Android app never called the coach chat endpoint

ChatViewModel.sendMessage() unconditionally emitted the generic WebSocket sendMessage event for every conversation, including the coach DM — there was no call anywhere to POST /coach/chat. A message sent from the app just posted as a normal chat message; CoachService.converse() was never invoked, so the dedicated "HabitFlow AI Assistant" chat overlay could show history but never produce a reply.

Fix applied (Android):

  • Added POST /coach/chat to HabitFlowApi.kt and ChatRepository.sendCoachMessage().
  • ChatViewModel.sendMessage() now calls the coach endpoint instead of the raw socket emit. The backend already persists and broadcasts both sides of the conversation over the same newMessage socket event the screen listens to, so no separate optimistic bubble is needed.
  • Fixed bot-vs-user bubble detection (was comparing senderId == "bot", but the real coach sender id is a Mongo ObjectId) — now compares against authManager.currentUserId, applied consistently to both the live socket listener and chat-history loading.

A second bug surfaced while testing the fix: ChatViewModel is created once at the nav-graph root and its old one-shot init {} fetched the coach chat id immediately — before login, or with a stale token from a prior session. If that first fetch failed, botChatId stayed null for the rest of the app session even after a fresh, successful login, leaving the assistant overlay permanently blank. Fixed by having the ViewModel collect authManager.accessToken and re-run setup every time a valid token appears, not just once at construction.

Verified: rebuilt and reinstalled on the emulator, reproduced the exact stale-token scenario (force-stopped the app, relaunched, logged in fresh), opened the AI Assistant overlay, and sent a real message from the on-screen keyboard — a real, specific reply ("Your completion rate over the last 7 days is 0%, putting your progress in the AT_RISK band...") arrived and rendered correctly as a bot bubble. Confirmed in the backend log as a clean coach agent run finished, no fallback.

Minor — not fixed

Coach identity in the Social-tab DM list isn't friendly

The coach conversation lists as "Unnamed Group" with sender shown as the raw ObjectId in the Social tab's generic Direct Messages screen (a separate UI surface from the dedicated AI Assistant overlay, which does have proper bot styling). That generic DM list also still sends via the plain chat socket, not POST /coach/chat — left as-is since the dedicated AI Assistant overlay is the real, designed entry point for talking to the coach; making every DM screen coach-aware was out of scope for this pass.

Minor — fixed as a side effect

Local demo seed data was stale

mongo-init.js only runs against a fresh Mongo volume (docker's docker-entrypoint-initdb.d convention), so the 8 documented demo accounts (demo.alex@habitflow.ai etc.) were never created on this already-initialized local volume, and one that did exist had a password hash from an older version of the seed script. Ran the (idempotent, guard-checked) seed script directly against the running container to add the missing users, and corrected the one stale password hash.

Minor — fixed

GOOGLE_MAPS_API_KEY missing from local env

Required by the Joi boot validation but absent from both apps/backend/.env and .env.example. Unrelated to AI, but blocked the app from starting at all. Added the real key to the local .env.

Quality — tuned

Coach replies read as robotic, especially for the Architect persona

The Architect persona description ("Thrives in systems, schedules, and predictable frameworks") was pushing the model to write literal systems-jargon — e.g. a real reply said "System efficiency is at 14 percent... assign every habit a fixed operational slot in your schedule to stabilize your routine." That's a persona trait taken too literally, not a persona voice.

Fix applied: added an explicit rule to both coach-phrasing.prompt.ts (Path B, used by check-in/weekly-review) and coach-agent.prompt.ts's system instruction (Path C, the reactive chat) telling the model to sound like a real coach talking to the person — contractions, everyday words — and never to turn a persona trait into literal jargon.

Verified — same scenario, before vs. after:

BEFORE

"Morning Run completed: 5km along the river before work. Current streak: 1 day. System efficiency is at 14 percent. Assign every habit a fixed operational slot in your schedule to stabilize your routine."

AFTER

"You got Morning Run done and logged your 5km along the river before work. Your streak is at 1 day. Let's look at the numbers: 14% completion this week means our current setup is leaking time. You need to assign every habit a fixed slot in your schedule so it runs on autopilot."

Same verdict, same numbers, same advice (the rule that forbids softening the assessment held) — just phrased like a person instead of a dashboard.

8. How to run it locally

# 1. Mongo
docker compose up -d

# 2. Backend (apps/backend/.env needs GEMINI_API_KEY, GOOGLE_MAPS_API_KEY, JWT_*,
#    GOOGLE_CLIENT_*, FIREBASE_* — Joi validates all of them on boot)
cd apps/backend && pnpm dev

# 3. Android — default BASE_URL (10.0.2.2:3000) already points at the local
#    backend from the emulator, no local.properties override needed
cd apps/android && ./gradlew installDebug   # needs JAVA_HOME = Android Studio's bundled JBR (21)

# 4. Talk to the coach from the app: tap the robot icon (top-left on Home/Map/
#    Profile) to open the "HabitFlow AI Assistant" overlay and send a message —
#    it now calls POST /coach/chat for real. Or exercise it directly:
curl -X POST localhost:3000/api/v1/coach/chat \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"message":"How am I doing this week?"}'
